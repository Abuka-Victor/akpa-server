# akpa server

The relay behind [akpa](https://github.com/Abuka-Victor/akpa-cli). It accepts
long-lived TCP connections from CLI clients, hands each one a public ID, and
proxies inbound browser traffic down to whichever client owns that ID.

Runs at **https://akpa.victorabuka.com**.

---

## What it does

Two listeners in one process:

| Port | Protocol | Who talks to it |
| --- | --- | --- |
| `7000` | raw TCP | akpa CLI clients, connection held open |
| `8081` | HTTP | browsers, and this site |

HTTP routes:

| Route | Purpose |
| --- | --- |
| `GET /` | Landing page |
| `GET /install.sh` | CLI installer script |
| `GET /live/{id}` | Proxied to the tunnel owning `{id}` |
| `GET /live/{id}/` | Same, subtree |
| `GET /static/…` | CSS, JS, favicon |

Tunnels live under `/live/` deliberately. Namespacing them keeps IDs from
colliding with real routes — without it, a tunnel ID of `install.sh` or `static`
would shadow the site itself.

## Running locally

```sh
git clone https://github.com/Abuka-Victor/akpa-server
cd akpa-server

go mod download
templ generate
npx tailwindcss -i ./static/css/input.css -o ./static/css/output.css

go run .
```

Open `http://localhost:8081`.

Then point a CLI at it:

```sh
akpa --relay localhost:8080 ~/some-folder
```

### Development loop

Both generators need to be running while you work:

```sh
templ generate --watch
npx tailwindcss -i ./static/css/input.css -o ./static/css/output.css --watch
```

> **Tailwind gotcha:** Tailwind only emits classes it can find in your source. If
> `.templ` files are not in the `content` glob, every class silently vanishes and
> the page renders unstyled. `tailwind.config.js` needs:
> ```js
> content: ["./**/*.templ", "./**/*_templ.go"]
> ```

> **templ gotcha:** editing a `.templ` file changes nothing until you run
> `templ generate`. The `_templ.go` files are what actually compile.

## Configuration

Uses `godotenv`, so a `.env` in the working directory is loaded at startup.

```ini
HTTP_ADDR=:8081
TCP_ADDR=:7000
PUBLIC_BASE=https://akpa.victorabuka.com
```


## Architecture

Each connected CLI is one entry in an in-memory registry keyed by tunnel ID. A
browser request to `/live/{id}/…` looks up that entry, writes the HTTP request
onto the client's connection, reads one response back, and streams it to the
browser.

Because tunnels are served from a path prefix rather than a subdomain, the server
injects `<base href="/live/{id}/">` into HTML responses so relative links resolve
correctly. This handles relative URLs only — absolute paths like `/logo.png` still
escape the prefix. Fine for directory listings, a real limit for arbitrary sites.

## Known limitations

Tracked and deliberate, not oversights. Roughly in priority order:

- [ ] **A new `bufio.Reader` is created per request.** Read-ahead means bytes
      buffered but not consumed are discarded, desyncing the connection on large
      responses. The reader should be created once per tunnel and reused.
- [ ] **No read/write deadlines.** A client whose laptop sleeps blocks the handler
      indefinitely.
- [ ] **The mutex is package-level.** One stalled tunnel blocks every other
      tunnel's requests. It should live inside the tunnel struct, guarding one
      socket.
- [ ] **One in-flight request per tunnel.** Requests serialise, so a page with
      many assets pays a round trip each. Fixing this means stream multiplexing.
- [ ] **Hop-by-hop headers are forwarded.** `Connection`, `Transfer-Encoding`, and
      friends should be stripped per RFC 7230 §6.1.
- [ ] **Only GET is routed.** `mux.HandleFunc("GET /live/{id}/", …)` returns 405
      for POST before the request ever reaches the CLI.
- [ ] **Query strings are mangled** by the `strings.Replace` path rewriting.
      Go 1.22's `{rest...}` wildcard removes the need for it.
- [ ] **No auth on the control port.** Anyone who can reach `:7000` can register a
      tunnel.
- [ ] **Registry is in-memory.** A restart drops every tunnel; can't scale
      horizontally.
- [ ] **No rate limiting** or per-tunnel request caps.
